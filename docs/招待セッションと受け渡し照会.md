# 招待セッションと受け渡し照会

試験運用では、3人がそれぞれの招待コードでログインし、画面を読み直しても自分の受け渡しを確認できます。Gateway がログインを確認し、コミュニティの API を呼ぶたびに Community Auth が Turso の `memberships` で有効な所属を確認します。

## Gateway に4つの Secret を登録する

| Secret 名 | 用途 |
| --- | --- |
| `RELAY_SESSION_KEY` | セッション Cookie の署名鍵 |
| `RELAY_INVITE_GIVER` | 出品者 `giver` の招待コード |
| `RELAY_INVITE_A` | 受取人 A `receiver-a` の招待コード |
| `RELAY_INVITE_B` | 受取人 B `receiver-b` の招待コード |

4つの値はそれぞれ独立に、暗号学的に安全な乱数を32バイト以上使って生成します。3人の所属は `db/community/demo_seed.sql` で登録します。

公開時は `ALLOW_DEMO_AUTH=false` を使い、`ALLOWED_ORIGINS` に公開する Web のオリジンを設定します。複数指定するときはカンマで区切ります。ローカルの既定値は `http://127.0.0.1:8787` と `http://localhost:8787` です。

`POST /api/v1/session` に招待コードを渡すと、署名付きの `relay_session` Cookie と、利用者の ID、表示名、有効期限が返ります。Cookie は8時間有効です。`GET /api/v1/session` で確認でき、`DELETE /api/v1/session` でブラウザから消せます。発行済み Cookie を一括で失効させる場合は署名鍵を交換します。

ログイン、ログアウトと Cookie 認証による更新では、`Origin` があれば `ALLOWED_ORIGINS` と照合します。サービス間の呼び出しでも使えるよう、`Origin` が無い要求は受け付けます。公開の入口を Web に絞り、Web 側でもブラウザからの更新要求を確認する前提です。

ログインに5回失敗すると、最初の試行から5分が経つまで同じ IP からの試行に `429` を返します。ログインに成功すると記録を消します。記録は Worker インスタンスのメモリに最大1,024件あり、上限に達すると古い記録を消します。再起動や別インスタンスには引き継がれません。IP が無い要求は同じ枠を使い、IP を共有する利用者は同じ制限を受けます。

Web と接続するときは、元の HTTPS URL、ブラウザの `Origin`、Cloudflare が付けた `CF-Connecting-IP` を Gateway に引き継ぎます。

## 繰り上がった利用者は自分の受け渡しを読み直せる

`GET /api/v1/communities/:communityId/listings/:listingId/matching` は、`listingStatus`、`viewerRole`、`applications`、`handoffs` を返します。出品者（`giver`）は応募一覧と受け渡しの進行中・履歴を参照できます。応募者（`applicant`）は本人の応募と受け渡しだけを参照でき、その他のメンバー（`none`）には空の配列が返ります。

出品直後はイベントが Matching に届くまで `404` が返ることがあります。応募・辞退などが Matching に書き込まれた後は、この API から読み直せます。セッションとコミュニティ API の応答には `Cache-Control: no-store` を付けます。

## 検証結果

型生成、Lint、型検査、全39テスト、全11パッケージのビルドが通りました。Gateway の試験で期限切れや改ざんの拒否を確認し、Matching の試験ではメモリ内の libSQL で、A の辞退後に B が自分の受け渡し ID を取得して完了できました。閲覧者ごとの開示範囲と、DB 障害時の応答もテストしています。

公開時は Web 経由で3人が別セッションから操作し、ログインから B の再読み込みと受け渡し完了まで確認します。
