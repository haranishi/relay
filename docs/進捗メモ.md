## 1. サービスの概要

Relayは、卒業・退職・異動などで不要になった家具や備品を、同じコミュニティの人へ期限内に引き継ぐ応募型マッチングサービスである。

最初は大学キャンパスを対象とする。

- 卒業生が、ソファ・机・家電などを出品する
- 「○月○日までに受け取れる方を募集」のように受渡期限を設定する
- 在学生がフリーマーケットのように出品を閲覧して応募する
- 出品者が第一候補と予備候補を選ぶ
- 第一候補が辞退した場合は、予備候補へ自動的に繰り上げる
- 実際の受渡しが終わったら取引を完了する

将来はキャンパス以外にも広げ、退職・異動する社員と同僚、地域住民、寮やシェアハウスなど、さまざまなコミュニティ内の受渡しに利用できるサービスを目指す。

## 2. 企画上の狙い

- 不用品を廃棄せず、必要とする人へ引き継ぐ
- 卒業や退去の期限がある譲渡を成立しやすくする
- 一般的なフリマサービスより、近距離での手渡しとコミュニティ内の信頼を重視する
- キャンパスで検証した仕組みを、企業や地域へ横展開する
- マイクロサービス、イベント駆動、疎結合設計、テスト、デプロイを授業成果として示す

## 3. 現在の主要要件

### 利用者

- 出品者: 卒業・退職・異動などを控え、物を譲りたい人
- 応募者: コミュニティに所属し、物を引き取りたい人
- 管理者: コミュニティの作成、参加資格、通報などを管理する人

### 基本機能

- コミュニティへの参加と在籍確認
- 出品の作成、編集、公開、締切
- 品名、説明、状態、受渡場所、受渡期限の登録
- 出品一覧と詳細の閲覧
- 出品への応募
- 第一候補と予備候補の選定
- 候補者の承諾または辞退
- 辞退時の繰り上げ
- 受渡し完了
- ドメインイベントによる他サービスへの状態反映
- 通知処理の境界

### 発表用デモフロー

1. 卒業予定者としてソファを出品する
2. 在学生Aと在学生Bが応募する
3. 出品者がAを第一候補、Bを予備候補にする
4. Aが辞退する
5. Bが繰り上げを承諾する
6. ソファの受渡しを完了する

### サービス構成

```text
Browser
  |
  v
Web Worker / Static Assets
  |
  v
API Gateway Worker
  |
  +--> Community Auth Worker --> Turso
  +--> Listing Worker --------> Turso / R2
  +--> Matching Worker -------> Turso
  +--> Read Model Worker -----> Turso

Listing / Matching
  |
  v
Transactional Outbox
  |
  v
Domain Events Queue
  |
  v
Event Router Worker
  |
  +--> Listing Commands Queue
  +--> Matching Commands Queue
  +--> Read Model Commands Queue
  +--> Notification Commands Queue
```

クラウド上では、バックエンドWorker 7個とWeb Worker 1個の合計8個を想定している。

## 7. 無料枠だけで運用する方針

### Cloudflare Workers Free

- リクエスト: アカウント全体で1日100,000回
- Worker数: 100個まで
- CPU時間: 1回10ms
- Cron Trigger: アカウント全体で5個まで
- 現在の予定: Worker 8個、Cron Trigger 2個

リクエスト数とWorker数には十分余裕がある。実デプロイ後は、Tursoへの通信待ちを除くCPU処理が10ms以内かを監視する。

### Cloudflare Queues Free

- 操作数: アカウント全体で1日10,000操作
- メッセージ保持: 24時間
- 通常は1メッセージにつき、書込み・読込み・削除の約3操作

授業デモには十分と見込む。再試行が増えると操作数を多く消費するため、エラーとDead Letter Queueを監視する。

### Cloudflare R2

- Standardストレージ: 月10GBまで無料
- Class A操作: 月100万回まで無料
- Class B操作: 月1,000万回まで無料
- 外部へのデータ転送: 無料

R2は無料枠を超えた場合に従量課金が発生し得る。Cloudflareの予算アラートは通知機能であり、利用を自動停止する上限ではない。

### 0円を確実に優先する場合

発表段階ではR2を使わず、デモ画像をCloudflare Static Assetsに含める構成が最も安全である。静的ファイルへのリクエストは無料・無制限で、R2のチェックアウトや超過課金を避けられる。

ただし、この構成では利用者が任意の画像をアップロードして保存する本番機能は扱わない。実画像アップロードを発表で見せる場合は、R2 Standardを有効化し、次のアプリ側制限を設ける。

- 1画像あたりの容量上限
- 1出品あたりの画像枚数上限
- 認証済み利用者だけがアップロード可能
- R2 bucketを非公開にし、Workerを経由してアクセス
- アップロード回数のRate Limit
- 古い画像の削除
- 利用量と請求画面の定期確認

## 8. 現在の重要な判断

画像について、次のどちらで発表するかを決める必要がある。

### A. 完全無料を最優先する構成

- R2を使わない
- 発表用固定画像をStatic Assetsで配信する
- 画像以外の出品・応募・候補選定・繰り上げを実クラウドで動かす
- 誤課金リスクが最も低い

### B. 実際の画像アップロードを見せる構成

- R2 Standardを有効化する
- 無料枠内で画像を保存する
- アップロード制限と監視を入れる
- デモ規模では0円の見込みだが、無料枠はハードな請求上限ではない

現在の希望である「無料枠だけに収める」を優先すると、まずAでデプロイする方針を推奨する。
