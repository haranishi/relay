## 1. サービスの概要

Relayは、卒業・退職・異動などで不要になった家具や備品を、同じコミュニティの人へ期限内に引き継ぐ応募型マッチングサービスである。

最初は大学キャンパスを対象とする。

- 卒業生が、ソファ・机・家電などを出品する
- 「○月○日までに受け取れる方を募集」のように受渡期限を設定する
- 在学生がフリーマーケットのように出品を閲覧して応募する
- 出品者が第一候補と予備候補を選ぶ
- 第一候補が辞退した場合は、予備候補へ自動的に繰り上げる
- 実際の受渡しが終わったら取引を完了する

将来はキャンパス以外にも広げ、退職・異動する社員と同僚、地域住民、寮やシェアハウスなど、さまざまなコミュニティ内の受渡しに利用できるサービスを目指す。

## 2. 企画上の狙い

- 不用品を廃棄せず、必要とする人へ引き継ぐ
- 卒業や退去の期限がある譲渡を成立しやすくする
- 一般的なフリマサービスより、近距離での手渡しとコミュニティ内の信頼を重視する
- キャンパスで検証した仕組みを、企業や地域へ横展開する
- マイクロサービス、イベント駆動、疎結合設計、テスト、デプロイを授業成果として示す

- 出品者: 卒業・退職・異動などを控え、物を譲りたい人

- 管理者: コミュニティの作成、参加資格、通報などを管理する人

### 基本機能

- コミュニティへの参加と在籍確認

- 出品一覧と詳細の閲覧
- 出品への応募
- 第一候補と予備候補の選定
- 候補者の承諾または辞退
- 辞退時の繰り上げ
- 受渡し完了
- ドメインイベントによる他サービスへの状態反映
- 通知処理の境界

### 発表用デモフロー

1. 卒業予定者としてソファを出品する
2. 在学生Aと在学生Bが応募する
3. 出品者がAを第一候補、Bを予備候補にする
4. Aが辞退する
5. Bが繰り上げを承諾する
6. ソファの受渡しを完了する

### サービス構成

```text
Browser
  |
  v
Web Worker / Static Assets
  |
  v
API Gateway Worker
  |
  +--> Community Auth Worker --> Turso
  +--> Listing Worker --------> Turso
  +--> Matching Worker -------> Turso
  +--> Read Model Worker -----> Turso

Listing / Matching
  |
  v
Transactional Outbox
  |
  v
Domain Events Queue
  |
  v
Event Router Worker
  |
  +--> Listing Commands Queue
  +--> Matching Commands Queue
  +--> Read Model Commands Queue
  +--> Notification Commands Queue
```

クラウド上では、バックエンドWorker 7個とWeb Worker 1個の合計8個を想定している。
公開URLはWeb Workerの `relay-web` のみに設定し、全WorkerのプレビューURLは無効にする。
Web Workerの `API_GATEWAY` バインディングで、試験運用に必要な API を Gateway に中継する。

## 7. 無料枠だけで運用する方針

### Cloudflare Workers Free

- リクエスト: アカウント全体で1日100,000回
- Worker数: 100個まで
- CPU時間: 1回10ms
- Cron Trigger: アカウント全体で5個まで
- 現在の予定: Worker 8個、Cron Trigger 2個

リクエスト数とWorker数には十分余裕がある。実デプロイ後は、Tursoへの通信待ちを除くCPU処理が10ms以内かを監視する。

### Cloudflare Queues Free

- 操作数: アカウント全体で1日10,000操作
- メッセージ保持: 24時間
- 通常は1メッセージにつき、書込み・読込み・削除の約3操作

授業デモには十分と見込む。再試行が増えると操作数を多く消費するため、エラーとDead Letter Queueを監視する。

### Cloudflare R2

- Standardストレージ: 月10GBまで無料
- Class A操作: 月100万回まで無料
- Class B操作: 月1,000万回まで無料
- 外部へのデータ転送: 無料

R2は無料枠を超えた場合に従量課金が発生し得る。Cloudflareの予算アラートは通知機能であり、利用を自動停止する上限ではない。

### 最初の公開での画像の扱い

最初の公開では画像を使わない。ソファの絵はCSSで描くため、R2の有効化やバケットの作成は不要。

将来、利用者の画像アップロードにR2 Standardを使う場合は、次の制限を設ける。

- 1画像あたりの容量上限
- 1出品あたりの画像枚数上限
- 認証済み利用者だけがアップロード可能
- R2 bucketを非公開にし、Workerを経由してアクセス
- アップロード回数のRate Limit
- 古い画像の削除
- 利用量と請求画面の定期確認

## 11. リスク・注意事項

- `/pilot` は、公開 URL で招待ログインと3人の操作を通して確認する必要がある
- Worker個別のテストは少なく、現在の自動テストは契約とドメインロジックが中心
- Workers Freeの1回10msのCPU制限：実測では、ページの表示で最大451msでも、2回の通し（計359回の呼び出し）で打ち切りは0だった。ただし上限は10msなので、混んだときの打ち切りは、Workerの Observability で `outcome = exceededCpu` を絞って監視する
- API Gatewayを再配備するときは、必ず `--var "ALLOWED_ORIGINS:<公開URL>"` を付ける。付け忘れるとlocalhostに戻り、ログインが403になる
- ListingとMatchingのコマンドQueueにはDLQがなく、5回失敗したメッセージは捨てられる
- Cronはアカウント全体で5本まで。Relayは2本を使うので、同じアカウントに足すときは空きを確かめる
- Queues Freeではメッセージが24時間で削除される
- R2を有効化する場合、無料枠超過を完全に停止する課金上限には頼れない
- Turso無料版では、長期間利用しないDBがアーカイブされる可能性がある
- 現在のプロジェクトフォルダはGitリポジトリとして初期化されていないため、クラウド作業前に履歴管理を始めることが望ましい
- SecretやTokenは、このメモやソースコードへ直接記載しない

### クラウドへの配備

- Turso（東京の `default` グループ）にDBを4個作り、移行を適用した。Cloudflareには、Queue 8個とWorker 8本を配備し、Secretを登録した。公開するのは `relay-web` だけで、内部の7本は外から404を返す。
- 実際の配備で見つかり、直した点：
  - 移行スクリプトが、リモート接続でだけ、台帳への記録で落ちた。リモートのトランザクションの `execute` は、引数を1つ（文）しか受け取らず、2つ目を捨てる。ローカルのファイルDBは受け取るので、試験で見つからなかった。`{ sql, args }` の形に直し、リモートと同じ形のクライアントで試験した。
  - Turso CLIのトークンの期限は、日単位（最短1日）か `never` だけで、`2h` は拒否される。手順書を `1d` に直した。
- 配備後の確認：公開URLで、疎通、認証の拒否、出品から受渡し完了までの通しが通った。スマホ幅の画面（Chromium・WebKit）でも、3人の操作の19項目が通った。出品がフィードに反映されるまでは約10秒。2回の通しで、計359回のWorkerの呼び出しがすべて成功し、例外は0だった。
- 独立の調査で見つかり、直した点：Matchingの `loadState()` が、5本のSELECTを同時に投げていた。リモートでは別々の通信になり、同時の更新が重なると、読みが食い違う可能性があった（実環境では再現していない）。`client.batch([...], "read")` の1回にまとめ、Matchingだけを再配備した。本物のTursoで読み取りのバッチが通ること、同じキーで選定を再送すると同じ受け渡しが200で返ることを確かめた（再送の本文は、項目と値が初回と同じで、キーの並び順だけが違う）。
