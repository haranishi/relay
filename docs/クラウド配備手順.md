# Relayのクラウド配備手順

WebからGatewayへの接続（`/pilot` と中継）は取り込み済みで、公開するのは `relay-web` だけです。○は読み取り確認、◆は本人の承認後に実行する操作です。

## 用意するリソースと無料枠

| 対象 | 名前と設定 |
| --- | --- |
| Turso DB 4個 | `relay-community-dev`、`relay-listing-dev`、`relay-matching-dev`、`relay-read-model-dev`。東京の `default` グループ。無料枠は全DBで読み取り月5億行、書き込み月1,000万行。10日無操作でアーカイブ |
| Queue 8個（うちDLQ 3個） | 名前は手順3を参照。無料枠は1日1万操作、メッセージ保持24時間 |
| Worker 8本 | 配備順は手順4を参照。無料枠は1日10万リクエスト、1回のCPU時間10ms。Cronはアカウントで5本まで。RelayはListingとMatchingで各1本を使う |
| Secret | DBを使う4本に `TURSO_DATABASE_URL`、`TURSO_AUTH_TOKEN`。Gatewayに `RELAY_SESSION_KEY`、`RELAY_INVITE_GIVER`、`RELAY_INVITE_A`、`RELAY_INVITE_B` |
| 公開URL | `https://relay-web.<アカウントのサブドメイン>.workers.dev` |
## 1. 配備先と公開URLを先に決める（○）

本人が選んだアカウントIDを指定します。過去の公開では、大学の `workers.dev` サブドメインは `haranishi`、ライラックは `lilac-webstudio00` でした。現行のWranglerには確認コマンドがないため、配備前にダッシュボードの「Workers と Pages」で確かめます。
Freeプラン、Cronの空き2本、名前の重複、Tursoの組織と東京の `default`、DBの空き、超過課金の設定も確認します。以下は2つのプレースホルダーを置き換え、リポジトリのルートから同じシェルで実行します。

```sh
export CLOUDFLARE_ACCOUNT_ID='<ACCOUNT_ID>' RELAY_PUBLIC_URL='https://relay-web.<WORKERS_SUBDOMAIN>.workers.dev'
export WRANGLER_WRITE_LOGS=false WRANGLER_LOG_SANITIZE=true
relay_turso() { "$HOME/.turso/turso" "$@"; }
relay_wr() { pnpm --dir apps/web exec wrangler "$@"; }
relay_turso group list && relay_wr queues list
```
## 2. DBを作って移行する（◆）

移行用の書き込みトークンは2時間で切れます（Worker用は手順3で別に発行します）。作成済みのDBでは `db create` の行を省きます。
```sh
(set +a +x -e
  for relay_service in community listing matching read-model; do
    relay_db="relay-$relay_service-dev"
    relay_turso db create "$relay_db" --group default --wait >/dev/null
    relay_db_url=$(relay_turso db show "$relay_db" --url 2>/dev/null)
    relay_db_token=$(relay_turso db tokens create "$relay_db" --expiration 2h 2>/dev/null)
    set -- "$relay_service" --apply
    [ "$relay_service" != community ] || set -- "$@" --demo-seed
    TURSO_DATABASE_URL="$relay_db_url" TURSO_AUTH_TOKEN="$relay_db_token" node scripts/cloud/apply-migrations.mjs "$@"
  done)
```
## 3. QueueとSecretを先にそろえる（◆）

```sh
(set -e
  for relay_queue in relay-domain-events-dlq-dev relay-read-model-dlq-dev relay-notification-dlq-dev \
    relay-domain-events-dev relay-listing-commands-dev relay-matching-commands-dev relay-read-model-commands-dev relay-notification-commands-dev; do
    relay_wr queues create "$relay_queue"
  done)
```

配備前にSecretを登録します。`secret bulk` が初回に失敗したら、権限 `0600` のJSONを作業ツリー外に置き、配備順に `wrangler deploy --secrets-file` を試します。Gatewayには生成したJSONを使います。
```sh
node scripts/cloud/gen-secrets.mjs                 # ローカルに作成。既存ファイルはそのまま使う
node scripts/cloud/provision-secrets.mjs --dry-run  # ○ Worker名とSecret名を確認
node scripts/cloud/provision-secrets.mjs --apply   # ◆ トークン発行と登録
```

Community Authのトークンは読み取り専用です。他の3本は読み書き用です。期限は30日で、失効前に同じ秘密ファイルで `--apply` を再実行して更新します。
## 4. 呼ばれる側から配備し、Webを公開する（◆）

```sh
(set -e
  pnpm -r --filter './packages/**' build
  for relay_worker in community-auth listing read-model notification matching event-router; do
    pnpm --dir "workers/$relay_worker" exec wrangler deploy
  done
  pnpm --dir workers/api-gateway exec wrangler deploy --var "ALLOWED_ORIGINS:$RELAY_PUBLIC_URL")
```

○ 内部Workerの `workers_dev` と全Workerの `preview_urls` が無効であることを確認します。◆ Webのビルドには `apps/web/public/og.png` と同じ公開URLを用意し、canonical・og:url・og:image を設定します。

```sh
test -f apps/web/public/og.png && NEXT_PUBLIC_SITE_URL="$RELAY_PUBLIC_URL" pnpm --filter @relay/web cf-build &&
  pnpm --dir apps/web exec opennextjs-cloudflare deploy
```
## 5. 公開先で確認し、3人に渡す前にデータを戻す

○ `node scripts/cloud/smoke.mjs "$RELAY_PUBLIC_URL"` で疎通と認証の拒否を確認します。◆ `node scripts/cloud/smoke.mjs "$RELAY_PUBLIC_URL" --flow` は架空の出品を1件作って受け渡し完了まで試します。
◆ `--flow` の後、送信待ちのイベントがなく、すべてのQueue（DLQを含む）にメッセージが残っていないことを確認します。配備先が静止してから3つのDBを空にします。3つすべてを空にしないと、削除した出品が一覧に残るなど、画面とDBの整合が崩れます。
```sh
(set +a +x -e
  for relay_service in listing matching read-model; do
    relay_db="relay-$relay_service-dev"
    relay_db_url=$(relay_turso db show "$relay_db" --url 2>/dev/null)
    relay_db_token=$(relay_turso db tokens create "$relay_db" --expiration 2h 2>/dev/null)
    TURSO_DATABASE_URL="$relay_db_url" TURSO_AUTH_TOKEN="$relay_db_token" node scripts/cloud/reset-pilot-data.mjs "$relay_service" --apply
  done)
```
一時のトークンは2時間で切れ、Worker用のトークンには影響しません。ループのあと、一覧が空であることを確かめてから3人に渡します。途中で止まった場合は、原因を直して3つのDBをそろえてから渡します。

## 落とし穴と復旧

- この家の回線では、過去の計測で `workers.dev` への通信が米国西海岸に向かい、1回の応答に0.4〜0.5秒かかったことがあります。体感が遅ければ、カスタムドメインを検討します。
- ◆ 10日無操作でTursoがアーカイブされたら、`relay_turso group unarchive default` で復元します。
- ◆ Workerを前のバージョンに戻すには `wrangler rollback` を対象の設定で実行します。停止時は配備の逆順に `wrangler delete` を実行します。QueueはWorkerを止めた後に `relay_wr queues delete '対象のQueue名'` で削除します。
- ◆ `relay_turso db destroy <DB名>` はデータごと削除します。対象を確認し、別途承認を得てから実行します。
- ◆ GatewayのSecretを入れ替える場合は別のパスにJSONを作り、`provision-secrets.mjs --apply --secrets <JSONのパス>` を使います。署名鍵を替えると全員のログインが切れます。
