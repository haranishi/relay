# 招待セッションと受け渡し照会

試験運用では、3人がそれぞれの招待コードでログインし、画面を読み直しても自分の受け渡しを確認できます。Gateway がログインを確認し、コミュニティの API を呼ぶたびに Community Auth が Turso の `memberships` で有効な所属を確認します。

## Gateway に4つの Secret を登録する

| Secret 名 | 用途 |
| --- | --- |
| `RELAY_SESSION_KEY` | セッション Cookie の署名鍵 |
| `RELAY_INVITE_GIVER` | 出品者 `giver` の招待コード |
| `RELAY_INVITE_A` | 受取人 A `receiver-a` の招待コード |
| `RELAY_INVITE_B` | 受取人 B `receiver-b` の招待コード |

4つの値はそれぞれ独立に、暗号学的に安全な乱数を32バイト以上使って生成します。3人の所属は `db/community/demo_seed.sql` で登録します。

公開時は `ALLOW_DEMO_AUTH=false` を使い、`ALLOWED_ORIGINS` を公開する Web のオリジンだけに置き換えます。配備後は、既定のローカルオリジン `http://127.0.0.1:8787` と `http://localhost:8787` が拒否されることを確認します。

`POST /api/v1/session` は JSON の本文を4,096バイトまで受け付けます。超えると `413` を返します。招待コードの入力は128文字までです。空白とハイフンを除き、全角と半角、大文字と小文字の違いをそろえて、登録済みのコードと照合します。

ログインすると、署名付きの `relay_session` Cookie と利用者の ID、表示名、有効期限が返ります。Cookie は8時間有効で、`Secure` を省くのはループバックの HTTP 接続だけです。`GET /api/v1/session` で確認できます。`DELETE /api/v1/session` でログアウトすると、ブラウザの Cookie だけを消します。サーバー側では発行済み Cookie が有効期限まで使えます。一括で失効させる場合は署名鍵を交換します。

ログイン、ログアウト、Cookie 認証による書き込みには `Origin` が必須です。`ALLOWED_ORIGINS` と完全に一致する場合だけ許可し、設定が未定義か空ならすべて拒否します。GET・HEAD・OPTIONS と、開発用のヘッダー認証によるコミュニティ API では `Origin` は不要です。

ログインの上限は同じ IP から5分間に失敗5回、要求全体で30回です。どちらかの上限に達すると、次の試行に `429` を返します。成功しても他の失敗は残り、`413` も失敗に数えます。共有回線で同じ IP を使う第三者が5回失敗すると、正規の利用者も最初の試行から5分が経つまでログインできません。

IP はそのまま使い、IPv6 を /64 に丸めません。IP が無い要求は同じ枠を使います。記録は Worker インスタンスのメモリに最大1,024件で、上限に達すると古いものから消します。再起動や別インスタンスには引き継がれません。十分に長いランダムな招待コードなら総当たりは現実的でないため、この制限は処理負荷とログの増加を抑えるために使います。

Web は、許可したパスを内部の HTTPS URL で Gateway に中継します。更新時はブラウザの `Origin` が Web 自身と一致することを確認し、`Origin` と Cloudflare が付けた `CF-Connecting-IP` を Gateway に引き継ぎます。

Worker のログはオーナーだけが読みます。Listing と Matching の API エラー、定期送信、キュー処理および Read Model のキュー処理では、DB の接続先とトークンを伏せます。エラー文にテーブル名や SQL が残ることがあります。

## 繰り上がった利用者は自分の受け渡しを読み直せる

`GET /api/v1/communities/:communityId/listings/:listingId/matching` は、`listingStatus`、`viewerRole`、`applications`、`handoffs` を返します。出品者（`giver`）は応募一覧と受け渡しの進行中・履歴を参照できます。応募者（`applicant`）は本人の応募と受け渡しだけを参照でき、その他のメンバー（`none`）には空の配列が返ります。

出品直後はイベントが Matching に届くまで `404` が返ることがあります。応募・辞退などが Matching に書き込まれた後は、この API から読み直せます。セッションとコミュニティ API の応答には `Cache-Control: no-store` を付けます。

## 検証結果

型生成、Lint、型検査、全62テスト、全11パッケージのビルドが通りました。Gateway の試験では本文の上限、招待コードの照合、回数制限、Origin と Cookie の条件を確認しました。Matching の試験ではログの伏せ字を確認し、メモリ内の libSQL で、A の辞退後に B が自分の受け渡し ID を取得して完了できました。閲覧者ごとの開示範囲と、DB 障害時の応答もテストしています。

公開時は Web 経由で3人が別セッションから操作し、ログインから B の再読み込みと受け渡し完了まで確認します。
